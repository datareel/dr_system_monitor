Plugins

Every DRSM check is a plugin: a folder with a small manifest and one BASH script. bin/drsm_run.sh finds the plugins each host needs, runs them, and writes the reports the dashboard and alerts use. Adding a check means adding a folder, not editing a core script.

Clientless and agent monitoring

DRSM checks a host in one of three ways. Each host file picks one with PLATFORM and COLLECTOR. For Linux, run clientless where you can and use the agent where you need it: one DRSM install can mix both kinds of host on the same dashboard. Windows hosts always use the agent.

HostModeHow it worksUse it when
LinuxClientless (COLLECTOR=ssh, or local for the monitor host)The monitor host logs in over SSH with a key and runs the plugins in one session. Nothing is installed on the host; the plugins are copied to ~/drsm_agent and only again when they change.The monitor host can reach the host over SSH: the same network, a VPN, or a cloud host with port 22 open to the monitor
LinuxAgent (COLLECTOR=lra)The DataReel Reporting Agent for Linux (drra, RHEL 8, 9 and 10) sends a report every 15 minutes by signed HTTPS upload (or CIFS, SCP). The linux/* plugins read the last report on the monitor side.DRSM cannot reach the host: behind NAT, on another network, no SSH from outside. Also for the vulnerability scans and the Vulnerabilities page
WindowsAgent only (COLLECTOR=wra)The DataReel Reporting Agent for Windows, a Windows service, sends its report every 15 minutes by signed HTTPS upload, a CIFS share or SCP. The windows/* plugins read the last report.Every Windows host. DRSM never connects to a Windows host, so there is no clientless mode for Windows

Agent hosts only make outgoing connections, to the report server pages (register.php, upload.php) on the dashboard's web server, so they can be anywhere on the internet. The monitor host does not need to reach them, and can even be the web server itself. Probes such as network/ping and network/https still run from the monitor host, so set PROBES="" for agent hosts it cannot reach.

The clientless Linux mode runs every Linux plugin, including storage/raid, storage/diskio, cloud/aws and cluster/drcm. The Linux agent reports CPU, load, memory, swap, disks, inodes, network, users, updates, security settings, failed services and vulnerability scans, with the same metric names as the clientless plugins, so the trends page shows both kinds of host the same way. See Windows hosts and Linux agent hosts.

Running checks with drsm_run.sh

$ ~/drsm/bin/drsm_run.sh -l             # list hosts and the plugins that would run
$ ~/drsm/bin/drsm_run.sh -n             # all hosts, no alerts
$ ~/drsm/bin/drsm_run.sh -n -H cloud1   # one host
$ ~/drsm/bin/drsm_run.sh -n -g dev      # the dev group
$ ~/drsm/bin/drsm_run.sh -m probes      # connectivity probes only

Host files

One file per host in etc/hosts, named <host>.conf. The files are plain KEY=value lines, read but never run, so a typo cannot execute anything. Values with spaces go in double quotes.

HOST=cloud1
DESCRIPTION="AWS web server"
IMPACT="Public website is down"
GROUP=production
PLATFORM=linux
COLLECTOR=ssh
PROBES="network/ping network/https"
PLUGINS="storage/disk storage/raid core/cpu core/load core/memory network/nics core/users"

# Plugin settings: <category>_<name>_<SETTING>=value
storage_disk_WARN=85
storage_disk_SKIP="/mnt/scratch"
network_https_URL=https://www.example.com/
core_cpu_TIMEOUT=60
KeyMeaning
HOSTName or address for SSH and probes, default is the file name
DESCRIPTION, IMPACTShown in reports and alerts
SITEOrganization and site, <org>/<site>, see Ansible inventoryOrganizations and sites
GROUPHost group and tier: ops (or production, the default), dev or qa, picked with drsm_run.sh -g
PLATFORMlinux or windows
COLLECTORssh, local for the monitor host itself, wra for Windows Reporting Agent hosts, lra for Linux agent hosts, none for probes only
ENABLEDno skips the host
PROBESPlugins run from the monitor host against this host
PLUGINSPlugins run on the host

_defaults.conf is read before every host file, so put the common PLUGINS list and site wide settings there. Files starting with _ are not hosts. If network/ping fails the host is reported down and its remote plugins are skipped.

To convert systems.dat, dev_systems.dat and the custom levels in <host>_profile.sh scripts, run utils/migrate_systems_dat.sh.

Ansible inventory

If your Linux hosts are already in an Ansible inventory, DRSM can use it as its host list, so there is one list to keep. Add to ~/.drsm.sh:

export ANSIBLE_INVENTORY=/etc/ansible/hosts
export ANSIBLE_TIERS="production=prod qa=qa dev=dev"   # tier=group[,group]
export ANSIBLE_DEFAULT_TIER=""                          # tier for other hosts, empty leaves them out
export ANSIBLE_SHORT_NAMES=yes                          # web1.example.com becomes web1
export ANSIBLE_EXCLUSIVE=no                             # yes: Linux hosts only from Ansible

With ANSIBLE_EXCLUSIVE=yes, Linux host files of hosts the inventory does not list are skipped, so removing a host from Ansible stops its checks from the next run; Windows and other host files still run, and so do probe only hosts (PLUGINS="" or COLLECTOR=none, such as cluster addresses). Its last report stays on the dashboard, shown as not reporting, until utils/drsm_remove_host.sh <host> --apply removes it.

Hosts in a group named in ANSIBLE_TIERS, or in any group under it through [group:children] at any depth, are checked as Linux hosts over SSH in that tier, with the _defaults.conf plugins. A host in two tiers goes to the first one listed. A host file with the same short or full name, or the same HOST=, adds settings such as DESCRIPTION, PLUGINS or plugin levels, but the tier always comes from Ansible. Host files for hosts Ansible does not list, such as Windows hosts and network devices, work as before. Check the result with drsm_run.sh -l.

Ansible Automation Platform or AWX

To read the inventory from Ansible Automation Platform (AAP, formerly Ansible Tower) or AWX instead of a file:

export ANSIBLE_AAP_URL=https://aap.example.com
export ANSIBLE_AAP_INVENTORY=12                     # ID or name
export ANSIBLE_AAP_TOKEN_FILE=~/.drsm_aap_token     # OAuth2 token, mode 600
export ANSIBLE_AAP_CA_FILE=""                       # CA bundle for a private CA
export ANSIBLE_AAP_CACHE_MINUTES=15
export ANSIBLE_AAP_API=""                           # empty tries /api/controller/v2, then /api/v2

DRSM fetches the inventory script (<api>/inventories/<id>/script/) with curl and jq, keeps an INI copy in $VARdir for the cache time and reads it like a local inventory with ANSIBLE_TIERS. AAP 2.5 and later serve the controller API at /api/controller/v2, older AAP, Tower and AWX at /api/v2; both are tried. The older ANSIBLE_TOWER_* names of these settings still work. If the platform cannot be reached, the last good copy is used and a warning is printed. A read-only token is enough; it is sent from a header file, not on the command line. utils/drsm_ansible_hosts.sh (-f to fetch now) lists the hosts and tiers DRSM takes from either source.

INI inventories are read: [group], [group:children], numeric ranges such as web[01:03].example.com; [group:vars] and host variables are skipped. YAML inventories are not read; ansible-inventory -i inv.yml --list can show their groups for an INI copy.

Organizations and sites

To monitor several customers or offices from one dashboard, put hosts in organizations and sites: organization > site > group > host. Each site has its own reports, alerts and card on the Organizations page, and two sites may have a host with the same name. Hosts in no site are in the default/default site, which keeps the reports where they have always been, so nothing changes until you add a site.

etc/sites/acme.org            # NAME="Acme Corp", CONTACT="..."
etc/sites/acme/hq.site        # the hq site of acme
Site keyMeaning
NAME, LOCATIONShown on the Organizations page
TZTime zone for the site's report times
ALERT_EMAILAlert addresses for the site, in place of alert.email.list
LINKA Site links menu entry, LINK="Menu/Submenu/Name|https://url|tier". Also in org files
ALERT_EMAIL_<TIER>Alert addresses for one tier at the site, for example ALERT_EMAIL_DEV, else ALERT_EMAIL
STALE_MINUTESWhen a host, or the site's monitor host, counts as not reporting, default 60
COLLECTOR_IDThe monitor host that runs the site. Others skip it. Unset, any monitor host runs it

Any host key or plugin setting in a site file is a default for the site's hosts, read after _defaults.conf and before the host file. GROUP is one too, so a whole site can be a QA or DEV site. A host joins a site with SITE=<org>/<site>, or every host of a monitor host with DRSM_SITE in ~/.drsm.sh. IDs use a-z, 0-9, _ and -.

Site reports go to reports/orgs/<org>/<site> with the usual layout inside, plus site.json. Each site has its own lock, log and alert throttle, and the alert subject names the site. Plugins get DRSM_ORG and DRSM_SITE.

Tiers

GROUP sorts hosts into tiers: dev, qa and ops. The dashboard shows them as DEV, QA and OPS, with a tier filter on the Organizations, Heat map and Hosts pages. ops is another name for production, the default group: ops hosts run with the production hosts, write the production report names with no _<group> suffix and get texts, so existing production files keep their names. Run each tier from cron:

15,45 * * * * ~/drsm/bin/drsm_run.sh &> /dev/null                # OPS
55 09-16 * * mon-fri ~/drsm/bin/drsm_run.sh -g dev &> /dev/null
55 09-16 * * mon-fri ~/drsm/bin/drsm_run.sh -g qa &> /dev/null

DEV and QA alerts never send texts. A site file can send each tier's alerts to its own addresses with ALERT_EMAIL_DEV, ALERT_EMAIL_QA and ALERT_EMAIL_OPS. A tier without one uses ALERT_EMAIL, then alert.email.list. Other group names still work and show as their own tier, in upper case.

Site links

Site and org files can list links for the dashboard's Site links menu, one LINK line each:

LINK="Wiki|https://wiki.example.com/"
LINK="Grafana/Database|https://grafana.example.com/d/db"
LINK="Apps/OSA/Admin|https://osa.example.com/admin|ops"

The first field is the name, and each / in it makes a submenu, up to six levels. The second is the URL: only http and https links are kept, others are reported by drsm_run.sh and skipped, and the dashboard checks them again. The optional third field is a tier: the link shows only when the tier filter is All or that tier. Links in <org>.org show for every site of the organization, in an Org links section of the same menu.

drsm_run.sh puts the links in site.json, so drsm_web_sync.sh takes them to a hosted dashboard, and users only see the links of sites they may see.

DRCM clusters

cluster/drcm watches a DataReel Cluster Manager (DRCM) cluster. Add it to the PLUGINS of every cluster node: each node reports what it sees, so a split cluster shows as two nodes that disagree.

PLUGINS="... cluster/drcm"
cluster_drcm_TUNNEL_SERVICES=drcm-tunnel   # node that runs the SSH tunnel
CheckState
drcm_server (SERVICE) and each unit in TUNNEL_SERVICES runningERROR when stopped
cm_stat: a node DownERROR
cm_stat: a node in Standby or Releasing (DRCM 1.43 maintenance), and the resources its peers run meanwhileSTANDBY_STATE, WARNING by default (INFO or ERROR)
cm_stat: a resource on its backup node (OK-Backup)FAILOVER_STATE, WARNING by default
cm_stat: one resource on two owners, duplicate resource, resources missingERROR (split cluster)
TCP connect to each active peer's keep_alive_ip:tcpport (LINK_CHECK)ERROR when it does not connect
Log: this node isolated (split brain fencing) and not yet resumedERROR
Log: missed keep alives in EVENT_MINUTES (30) at or over KEEPALIVE_WARN (3)WARNING
Log: no "is alive" line from a peer for KEEPALIVE_STALE seconds (300)WARNING
Log: failover, failback, isolation and takeover check events in EVENT_MINUTESFAILOVER_STATE
Log: resource script errors in EVENT_MINUTESERROR

The plugin only reads: drcm_server --client --command=cm_stat, the cluster config (CM_CONFIG, default /etc/drcm/cm.cfg) and the cluster log named by its log_dir and logfile. The DRSM account needs read access to /etc/drcm/.auth for cm_stat, for example through a drcm group that owns it (mode 640); without it the cluster status is UNKNOWN and the other checks still run. Metrics for the trends page: drcm_nodes_up, drcm_nodes_down, drcm_resources, drcm_resources_failed_over, drcm_keepalive_misses, drcm_failover_events, drcm_nodes_standby, and per peer drcm_keepalive_ok and drcm_keepalive_missed for the last INTERVAL_MINUTES (15, the cron interval).

The plugin also prints DRCM kind|... lines for the Clusters page: nodes, resources, links, health, a keep alive timeline per peer for the last STRIP_HOURS in STRIP_STEP second steps, and the log events. The host page hides them. CLUSTER_NAME names the cluster on that page; by default it is the node names joined with +.

On Linux agent hosts (COLLECTOR=lra) DRSM cannot run the check: it runs on each node as the agent's drcm report hook instead, see Report hooks.

Windows hosts

Windows hosts run the Windows Reporting Agent, a small Windows service from the agent distribution. Every 45 minutes it sends a text report (installed programs, Windows Defender events, Windows Update history, hotfixes, users, IP addresses) to the monitor side by signed HTTPS upload, a CIFS share, or SCP. DRSM never connects to the Windows host: the wra collector runs the windows/* plugins on the monitor host against each host's last report, $WRA_REPORTS_DIR/<host>_windows_report_agent.txt.

A Windows host file, also in etc/hosts/windows.conf_example:

HOST=laptop1
PLATFORM=windows
COLLECTOR=wra
PROBES=""
PLUGINS="windows/checkin windows/defender windows/patches windows/apps windows/resources"

PROBES="" turns off the ping probe, laptops move between networks. Set WRA_REPORTS_DIR once in _defaults.conf: it is reports_dir from the agent's server.ini, or the folder the CIFS or SCP delivery writes to. The default is /var/www/html/windows/reports. Set WRA_NAME when the agent reports under a name other than HOST. Linux plugins in _defaults.conf are skipped on Windows hosts.

For many hosts, utils/wra_hosts.sh makes one host file per report. It only lists what it would write until run with --apply, and never changes a host file that exists:

$ ~/drsm/utils/wra_hosts.sh -d /var/www/html/windows/reports
$ ~/drsm/utils/wra_hosts.sh -d /var/www/html/windows/reports --apply

    bash ~/drsm/plugins/windows/checkin/check.sh

Linux agent hosts

DRSM checks most Linux hosts over SSH with the core plugins, and needs nothing installed on them (the clientless mode). For a Linux host DRSM cannot reach, such as a cloud server behind NAT or on another network, install the DataReel Reporting Agent for Linux (drra), a systemd service for RHEL 8, 9 and 10. Every 15 minutes it sends a report on its host to the report server pages (register.php, upload.php) by signed HTTPS upload, the same protocol as the Windows agent, or by a CIFS share or SCP. The host only makes outgoing TLS connections. The lra collector runs the linux/* plugins on the monitor host against each host's last report, ${LRA_REPORTS_DIR}/<host>_linux_report_agent.txt.

A Linux agent host file, also in etc/hosts/linux_agent.conf_example:

HOST=web1
PLATFORM=linux
COLLECTOR=lra
PROBES=""
PLUGINS="linux/checkin linux/resources linux/updates linux/security linux/vulnerabilities"

Set PLUGINS in the host file: the core plugins in _defaults.conf are Linux plugins too, and with this collector they would check the monitor host. PROBES="" turns off the ping probe; keep probes such as network/https for hosts the monitor can reach. Set LRA_REPORTS_DIR once in _defaults.conf: it is reports_dir from the report server's server.ini, or the folder the CIFS or SCP delivery writes to. The default is /var/www/html/linux/reports. The DRSM account needs read access to it. Set LRA_NAME when the agent reports under a name other than HOST.

For many hosts, utils/lra_hosts.sh makes one host file per report. It only lists what it would write until run with --apply, and never changes a host file that exists:

$ ~/drsm/utils/lra_hosts.sh -d /var/www/html/linux/reports

The severities are Critical, Important, Moderate, Low, or none. linux/resources uses the metric names of the core and storage plugins (cpu_used_pct, load_15m, mem_available_mb, swap_used_mb, disk_used_pct{mount="/"}, nic_rx_bytes{nic="eno1"} and so on, plus sample_etime), so agent hosts get the same gauges and trends as SSH hosts. The other plugins add updates_pending, updates_last_days, reboot_required, failed_units, user_sessions, lra_report_age_seconds, vuln_critical, vuln_important, vuln_moderate, vuln_low, vuln_total, vuln_cves, vuln_unfixed, compliance_score and compliance_fail.

The vulnerability scan is off in the agent by default (an OpenSCAP scan can use about 800 MB of memory); turn it on per host with [scan] enabled=1 in /etc/drra/drra.ini. A host with the scan off is OK with an INFO line, and the Vulnerabilities page names it. The agent then scans once a day. On RHEL 8 and 9 it runs OpenSCAP against Red Hat's OVAL feed (source oval) and uploads the OpenSCAP HTML report too. RHEL 10 has no OVAL feed, so the agent matches its packages against an index of Red Hat's CSAF/VEX files that the report server builds (vex_sync.php from cron, served by vex_index.php), plus dnf errata newer than the VEX files (source csaf). That scan also counts CVEs with no fix yet. dnf (dnf updateinfo) is the fallback. An optional OpenSCAP compliance scan (a CIS or STIG profile, off by default in the agent) adds a score and the failed rules.

linux/vulnerabilities prints these lines for the Vulnerabilities page; the host page hides them:

VULN summary|source|scan_etime|critical|important|moderate|low|unknown|total|cves|status|unfixed
VULN advisory|id|severity|issued|cves|packages|title
VULN unfixed|cve|severity|packages|state
VULN compliance|profile|score|pass|fail|scan_etime
VULN rule|rule|severity

status is ok, failed, pending or disabled; unfixed is empty when the scan cannot tell.

A host that has never sent a report, or whose report file is empty, is an ERROR from linux/checkin; the other Linux agent plugins are UNKNOWN until a report arrives. To run one by hand:

$ DRSM_TARGET=web1 DRSM_LRA_REPORT=/var/www/html/linux/reports/web1_linux_report_agent.txt \
    bash ~/drsm/plugins/linux/vulnerabilities/check.sh

Report hooks

Checks that must run on an agent host, such as cluster/drcm, run as the agent's report hooks: executable files in /etc/drra/report.d on the host (agent 1.0-beta2 and later). The agent runs each one with every report and puts its output and exit code in the report's HOOKS section. On the monitor:

  • A plugin whose manifest sets LRA_HOOK=<name> shows hook <name> as its own check on COLLECTOR=lra hosts, in place of running here (cluster/drcm has LRA_HOOK=drcm, so the Clusters page works for agent hosts). A hook that is missing is UNKNOWN, one that timed out or that the agent skipped is an ERROR. Set <category>_<name>_LRA_HOOK=NONE in a host file to turn this off.
  • linux/hooks shows every hook, each with its output, and takes the worst exit code. List the hooks a plugin already shows in SKIP (default NONE); NONE_OK=1 makes a report with no hooks OK.
  • utils/lra_hook_bundle.sh writes a plugin as one self-contained hook file, with the manifest defaults, the -f host file settings and KEY=value arguments built in.
$ ~/drsm/utils/lra_hook_bundle.sh -f ~/drsm/etc/hosts/node1.conf cluster/drcm > drcm
$ scp drcm node1:
$ ssh node1 'sudo install -o root -g root -m 0755 drcm /etc/drra/report.d/drcm && sudo drra hooks'

Then add the plugin to the host's PLUGINS. Any script can be a hook: it prints DRSM plugin lines (INFO - , WARNING - , ERROR - , METRIC, DETAIL) and exits 0, 1, 2 or 3. Plugins that read agent reports (linux/*) cannot be bundled.

Writing a plugin

$ ~/drsm/utils/new_plugin.sh local/myapp            # runs on the host
$ ~/drsm/utils/new_plugin.sh local/myapp_url probe  # runs from the monitor against the host

This creates the folder, a commented plugin.conf, and a script you can run by hand right away:

$ DRSM_WARN=50 bash ~/drsm/plugins/local/myapp/check.sh
$ DRSM_TARGET=cloud1 bash ~/drsm/plugins/local/myapp_url/probe.sh

Then add local/myapp to PLUGINS (or PROBES) in a host file. Site plugins live in plugins/local, which updates never overwrite.

Manifest

NAME=myapp
CATEGORY=local
DESCRIPTION="Order queue is draining"
PLATFORMS="linux"      # linux, windows, or any
MODE=remote            # remote runs check.sh on the host, probe runs probe.sh on the monitor
TIMEOUT=30             # seconds, enforced by the runner
REQUIRES="curl jq"     # commands that must exist, otherwise the plugin is UNKNOWN
NEEDS_SUDO=no          # informational: no, yes, or optional

# Every other key is a setting with its default
WARN=100
CRIT=500
QUEUE_DIR=/var/spool/myapp

Each setting reaches the script as DRSM_<KEY>. A host overrides it with <category>_<name>_<KEY>, for example local_myapp_WARN=200, and can set <category>_<name>_TIMEOUT.

Script

#!/bin/bash
source "${DRSM_LIB:-$(dirname "$0")/../../../lib}/drsm_plugin.sh"

WARN=$(drsm_setting WARN 100)
CRIT=$(drsm_setting CRIT 500)
QUEUE_DIR=$(drsm_setting QUEUE_DIR /var/spool/myapp)

count=$(find "${QUEUE_DIR}" -type f | wc -l)
if [ "${count}" -ge "${CRIT}" ]; then
    drsm_crit "${HOST} myapp queue has ${count} files"
elif [ "${count}" -ge "${WARN}" ]; then
    drsm_warn "${HOST} myapp queue has ${count} files"
else
    drsm_ok "${HOST} myapp queue checks good at ${count} files"
fi
drsm_metric myapp_queue_files "${count}"

States and exit codes

Exit codes follow the Nagios plugin convention:

0 OK 1 WARNING 2 ERROR 3 UNKNOWN

  • An ERROR - or WARNING - line counts even if the script exits 0.
  • A plugin that runs past its TIMEOUT is stopped and reported as a WARNING.
  • A missing REQUIRES command makes the plugin UNKNOWN, which shows in the report but does not alert.
  • A plugin that prints nothing is reported as an ERROR.

How a run works

For each host the runner builds one job script with a line per plugin, its settings and its timeout. Probe jobs run on the monitor host. Remote jobs go through the host's collector:

  • local runs the job in place from $DRSMHOME.
  • wra runs the windows/* plugins in place from $DRSMHOME against the host's last Windows Reporting Agent report, see Windows hosts.
  • lra runs the linux/* plugins in place from $DRSMHOME against the host's last DataReel Reporting Agent for Linux report, see Linux agent hosts.
  • ssh-linux copies lib/drsm_plugin.sh and the host's plugins to ~/drsm_agent as one tar stream, skipped when the checksum has not changed, then runs the whole job in one SSH session. Set DRSM_REMOTE_BASE for another directory.

Roadmap

Later phases of the plugin design add more checks (SMART, mounts, backup age, TCP ports, TLS expiry, DNS, time sync, failed services), generic database, container, service and process plugins with a custom/command catch all, and configurable notifiers (email, SMS, Slack, ntfy, webhook) with alert on change.
